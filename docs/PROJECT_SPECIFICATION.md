# ReplayProof — Project specification and acceptance criteria

> Original backend scope and acceptance brief. Executed results are documented in VERIFICATION.md; subsequent frontend scope is documented in ARCHITECTURE_DECISIONS.md.

## Backend requirements

Build **ReplayProof: a fault-tolerant, sequence-aware market-event ingestion and forensic reconciliation service** in this repository. The goal is a differentiated, recruiter-verifiable 2027 new-grad backend/SDE portfolio project, NOT a generic CRUD application, wallet clone, trading bot, alpha backtester, high-frequency exchange simulator, or decorative microservices diagram.

### Mission, user context, and nonnegotiables

The project demonstrates relational database design, SQL, transactions, multi-process concurrency, event ordering, failure recovery, reconciliation, and diagnostics within a bounded synthetic-data service. Prefer a small, verifiable implementation over architectural scope.

Build only with **synthetic market-event data**. Do not scrape exchanges or integrate real brokers, financial accounts, payment services, production credentials, licensed datasets, or cloud infrastructure. Do not implement strategy alpha, profitability claims, a web UI, Kafka, Kubernetes, Redis, Celery, or microservices in the MVP. A single FastAPI service and PostgreSQL database are enough. Do not say “production-ready” or “exactly-once delivery”; define only the correctness properties we can actually demonstrate.

**Mandatory stack:** Python 3.12 (or 3.11 if environment forces it), FastAPI, PostgreSQL 16+, SQLAlchemy 2.x, Alembic, Pydantic v2, pytest, httpx, Docker Compose, Ruff, MyPy, GitHub Actions. Prefer `uv` for project management if it is practical in the environment. Use standard SQL rather than adding a separate analytics warehouse. Use sync SQLAlchemy sessions/standard `def` API routes if that makes transaction reasoning clearer; never add nominal async without a defensible need. PostgreSQL, not SQLite, is mandatory for concurrency tests.

### Product semantics (do not silently change)

A `stream` represents **one synthetic feed session for one instrument** and begins at sequence number 1. Events are simulated immutable trade prints. A canonical event includes:

- `stream_id` (UUID, generated by our service when stream is created);
- `sequence` (strictly positive integer unique within stream);
- `source_event_id` (stable string identifier, unique within the stream for the MVP);
- `event_time` (timezone-aware UTC timestamp; normalize for canonical hashing);
- `price_ticks` (positive integer representing price in an explicitly documented fixed price scale; avoid floats);
- `quantity` (strictly positive integer);
- `schema_version` (=1 for MVP).

Assume the simulated source assigns complete, consecutive sequences starting at 1. A missing number within the highest seen sequence is therefore a gap. **Do not infer gaps after the highest received sequence.** Arrival can be out-of-order and repeated. Event timestamps are NOT guaranteed to follow sequence order; one newly applied event may belong to an earlier minute. Same `(stream_id, sequence)` + canonically identical fields is a retry; same `(stream_id, sequence)` + differing canonical payload is an integrity conflict that must be recorded and must never silently overwrite the original. Avoid ambiguous identity: if `source_event_id` reappears at a different sequence, quarantine/reject as a separate conflict. Do not add trade cancels, amendments, venue-specific packets, or real exchange protocols to the MVP.

Derived view: 1-minute UTC OHLCV `bars` with `open`, `high`, `low`, `close`, `volume`, `trade_count`; select open/close **by `(event_time, sequence)`**, not HTTP arrival order or only sequence order. Minutes are `[minute_start, minute_start + 60s)`. Aggregate high/low and volume/count with integer arithmetic. **Bars remain provisional**: a higher-sequence event may have an older `event_time` and change a historical minute. Do not label bars final without a separately justified watermark/completeness contract.

### Persistence model and invariants

Use Alembic migrations and clear SQL constraints. At minimum:

- `streams`: `id`, `symbol`, `last_applied_seq` (starts 0), `max_received_seq` or derive from canonical events, `created_at`; add a check `last_applied_seq >= 0`.
- `source_events`: UUID/PK, `stream_id`, `sequence`, `source_event_id`, event timestamp, scaled integer price, quantity, schema version, `payload_sha256`, `received_at`, with unique `(stream_id, sequence)` and `(stream_id, source_event_id)`. Event business fields stay immutable; application never overwrites them.
- `bars`: unique `(stream_id, minute_start)`, integer OHLCV/count and sufficient tie-break metadata or deterministic recomputation to maintain correctness after out-of-time arrivals.
- `integrity_conflicts`: immutable audit entries storing stream/sequence and conflicting fingerprints or sanitized payload metadata, timestamps, category, and reason.
- `reconciliation_runs` and optionally `reconciliation_diffs`: id, stream, observed cursor, timestamp, status, digest, count, and concrete mismatches with expected/actual values. Avoid storing excessive raw payloads or secrets.

Every accepted event is stored durably before or atomically with projection, under one PostgreSQL transaction. A per-stream lock (`SELECT ... FOR UPDATE` on `streams`) serializes accepted state transitions **across API processes**. All ingestion paths must use this lock; no Python process-level lock pretends to protect multi-process writes. Use PostgreSQL uniqueness as the final arbiter of duplicates and handle transactional race outcomes. When an event arrives, store it, then apply only the maximal **contiguous prefix** starting at `last_applied_seq + 1`, in strictly increasing sequence order, updating bars and cursor in the **same database transaction**. A future event remains durably buffered but unapplied until gaps are filled. Roll back the entire transaction on unexpected projection failure.

Use a correct and explainable approach for historical bars when a newly applied higher-sequence event has an older timestamp: recompute **each touched minute** from canonical applied events (`sequence <= last_applied_seq` including the new prefix), or maintain carefully tested boundary metadata and counts. Prefer recomputation for correctness and scope; document its cost and why a higher-volume system would change it. Avoid N+1 queries where an easy bounded group operation exists.

**Invariant I1 — prefix:** after commit, processed source sequences equal exactly `1..last_applied_seq` (no holes, no repeated economic/analytic effect).

**I2 — duplicate safety:** same source sequence + identical payload does not change rows in `source_events` or `bars`, and returns a stable dedup response. Different payload at same sequence produces HTTP 409 and an audit conflict; previously accepted data stays unchanged.

**I3 — projection accuracy:** each materialized OHLCV bar equals the aggregation of stored canonical applied events by `(event_time, sequence)` order, independent of arrival order.

**I4 — crash safety:** exceptions before commit leave no partial event/cursor/bar state; a client retry after a commit succeeds without second application, including when original HTTP response was lost.

**I5 — recovery:** events buffered beyond a gap become applied in order once missing events are recovered through the *normal* ingestion path, with no alternate backdoor to mutate aggregates.

**I6 — forensic reconciliation:** a separate, independently implemented **SQL-based reference aggregation** flags any corrupt/materially missing/extra derived bars. It must not merely call the same Python reducer that produced the online view. The report identifies exact minute buckets and expected vs actual fields. Reconciliation must operate against a consistent snapshot or appropriate stream lock to avoid false mismatch during concurrent writes. A controlled local rebuild restores correct bars atomically and leaves source events untouched.

**I7 — reproducibility:** for equal source-event sets, replayed in ordered, shuffled, duplicated, and concurrent arrival patterns (with eventual gap-fill), normalized final bar outputs and deterministic hashes match exactly.

Explain any limitations of unique-key assumptions, stream cursor contention, backpressure, missing event permanence, clock behavior and lack of an external true source of truth.

### API and CLI contracts (small, stable)

- `POST /v1/streams`: create synthetic stream, return UUID and symbol.
- `POST /v1/streams/{id}/events`: accept one validated event; return status among `applied`, `buffered`, `duplicate`; the same seq + different fingerprint returns 409. Include cursor and meaningful details.
- `POST /v1/streams/{id}/events/batch`: OPTIONAL until core single-event correctness is established; if implemented, document whether all-or-nothing or per-event commit; favor safe bounded batch size and consistent semantics.
- `GET /v1/streams/{id}/status`: last applied, highest received, buffered count, inferred gap ranges within seen high watermark, conflict count, whether blocked by gaps.
- `GET /v1/streams/{id}/bars?start=&end=`: time-bounded, paginated bars with `provisional: true` and explicit price scale.
- `POST /v1/streams/{id}/reconcile`: generate and persist independently calculated comparison/report; return reconciliation id and mismatch summary.
- `GET /v1/reconciliations/{run_id}`: retrieve evidence, bounded mismatch list, and digest.
- `POST /v1/streams/{id}/rebuild`: local/dev-only operator action, gated behind an explicit environment flag and intentionally inaccessible when disabled; atomically reconstruct bars from canonical applied events, under stream lock. Report before/after digest and changed bucket count. Never expose destructive mutation unauthenticated on a public server.
- `GET /health/live`, `GET /health/ready`: health and PostgreSQL readiness.

Provide `python -m replayproof.cli demo --seed 2027` (or a comparably simple documented command) that runs deterministic scenarios on a local Docker stack. It should visibly demonstrate: baseline ordered ingestion; a deliberately withheld sequence that blocks the applied cursor while later events buffer; replay of the missing record; duplicate retry; conflicting duplicate quarantined; a locally injected **test-only** bar corruption detected by independent reconciliation and fixed by rebuild; final deterministic checksum match. A CLI/terminal explanation is sufficient; NO frontend.

### The differentiator: executable forensic incident

Create a stable, machine-readable artifact after the demo in `artifacts/demo/` or a configurable output directory:

- `incident.json`: generated seed, scenario parameters, stream IDs, sequence gaps, failures injected, status transitions, repair actions, outcome and timestamps;
- `reconciliation_before.json` and `reconciliation_after.json`: mismatches and corrected counts;
- `digest_comparison.json`: ordered-versus-disrupted normalized projection SHA-256 hashes, whether equal, and raw event/aggregation counts;
- a concise human-readable incident narrative explaining **what failed, what would have been incorrect, how the system detected it, and how correctness was restored**.

No handwritten “example performance results” masquerading as measurements. The demo must generate real artifacts from executed commands. Use local deliberate corruption only in a named development/test helper, not a public endpoint. This is a *forensic, reproducible backend correctness case study*, not “data visualization.”

### Test strategy: quality gates, not test-count theater

Write **PostgreSQL-backed integration tests**, unit tests for pure event/bucket functions, concurrency tests with independent DB connections and independent API processes where feasible, and property/metamorphic tests (Hypothesis optional). Include at least the following independently verifiable cases:

1. Reject zero/negative seq, prices or quantity, naive timestamps, unknown fields/symbol injection where applicable.
2. Detect malformed source IDs and timestamps; avoid integer overflow via database/Pydantic checks.
3. 1..N ordered events -> all applied; identical idempotent retries -> no changes.
4. Submit sequences 1,2,4,5 then assert cursor 2 and bars reflect ONLY first two; submit 3 and assert cursor 5 and bars correct.
5. Multiple nonadjacent gaps, and a missing last event with no later arrival must NOT be falsely diagnosed.
6. Duplicate request sent simultaneously from multiple DB sessions/processes -> single source row and stable projection.
7. Same sequence/different fingerprint and same source_event_id/different sequence -> 409 and recorded conflict, no mutation of accepted source.
8. Trade timestamps arrive earlier than their sequence neighbors, including crosses over minute boundaries, and OHLCV open/close are correct by event_time plus sequence tie-break.
9. Failed DB transaction partway through projection -> rollback of source/cursor/bars; retry works. Inject failure deterministically in test code; no uncontrolled flaky process killing.
10. A committed event with a simulated lost HTTP response -> subsequent retry deduplicates safely.
11. Concurrent mixed-stream traffic doesn't corrupt per-stream cursors or affect independent streams.
12. Three different random arrival orders from same seed -> byte-identical normalized final bars and equal digest after recovery.
13. SQL oracle and online reducer agree on nontrivial data, including tied event timestamps and out-of-order event times.
14. Deliberately change a materialized bar locally, run reconciliation, verify specific mismatch, trigger dev rebuild and verify no mismatches. Also test omitted/extra bar rows.
15. Reconciliation during ingestion either uses a stable DB snapshot or documented serialization and produces no false positives.
16. Fresh database migrate-up smoke test, `docker compose up --build`, clean restart with durable state, CI lint/type/test jobs.

Make the independent reconciliation use SQL window functions/aggregates or another independent SQL strategy, not the online Python function renamed. Explain `READ COMMITTED` vs `REPEATABLE READ` or locks for consistent comparison. Prove stable digest serialization (ordering, timezone, price scale). If a meaningful test fails, fix semantics rather than weakening the assertion.
